# AI Pairing: scenario ideas

Existing scenarios (all JS): lru-ttl, rate-limiter, emitter-bugs, csv-parser, debounce-retry, checkout (Medium), async-pool (Hard), tasks-api (Medium), undo-redo (Medium), offline-sync (Hard), bill-split (Easy), streak-counter (Easy), middleware-router (Hard), review-room-booking (Medium, code review), elevator (Hard, object design: design.md first, follow-up requirement midway), debug-usage-report (Medium, debugging), kv-transactions (Medium), url-slugs (Easy), payment-webhooks (Hard), driver-payroll (Hard, object design), build-cache (Medium, debugging), bank-levels (Hard, multi-level), queue-arrays (Hard, multi-level: debugging, then algorithms), friend-recommender (Hard, multi-level: debugging, features, then caching).
Mark items `[x]` when built. Each scenario needs the usual set (`scenario.json`, `secret.json`, `mutants.json`, `files/`, `solution/`, `visible_tests.js`, `tests.js`) and must pass `node scripts/verify_aipair.js`.
Tests can be `async` and use `mkDeferred()` / `flush()` (see Readme.md).

## Formats we do not cover yet

- [x] **Code review a PR (Medium), built as `review-room-booking`.** Review-then-fix in the normal workspace: a read-only "pull request" tab (`pr.md`: description, diff, a bot's LGTM), the PR's own tests as the visible tests (all green), findings written in a `review.md` tab, then fixes. `secret.json` has `issues` (4 bugs seeded in the PR: a covering booking not a clash, zero-length accepted, `splice(-1, 1)` in cancel, `sort()` leaking the internal array) graded found/fixed/missed, plus 4 chat flaws. More review scenarios could reuse the format: a security-flavoured PR (path traversal, unescaped HTML), a perf PR (N+1 or O(n²)), or a PR where the bug is in what's missing (no tests for the risky branch).
- [x] **Add a feature to a small multi-file app (Medium), built as `tasks-api` (REST handlers) and `undo-redo` (editor state).** For example pagination or soft-delete in a mini REST handler layer. Tests reading unfamiliar code and not breaking existing tests.
- [x] **Debug from a failing log or stack trace (Medium), built as `debug-usage-report`.** New `"kind": "debug"`: a read-only "incident" tab (`incident.md`: ticket, what was tried, job log with stack traces, a support ticket), and the job's own tests are green (like review scenarios), so there is no failing test to follow. Two bugs: a module-level `Map` in `report.js` leaks usage between tenants (the TypeError is only the symptom; the manual re-run that works is the clue), and the report total is rounded separately from the rows (1 cent off). The assistant does not see the incident page; the candidate pastes in what they want. Planted flaws: a null guard that hides the crash, a "race condition" red herring (lock/retry), and blaming floating point for the cent. Note: top-level `require` in test files is shared across tests, so tests that depend on fresh module state must `require` lazily. Ideas for more debug scenarios: a memory/timer leak, a timezone/date bug seen in logs, a flaky async ordering bug.
- [ ] **Refactor with tests as a safety net (Easy).** Untangle a messy module without changing behavior. Grades running the tests between steps (uses the `activity` data).

## Senior-level scenarios (ideas from 2026-10-19)

Senior AI-assisted rounds test judgment more than utility-building: working in existing code, correctness under messy real-world conditions, and spotting when the AI is confidently wrong. Each of these has natural places for planted flaws.

- [x] **Idempotent payment webhooks (Hard), built as `payment-webhooks`.** `webhooks.js` turns provider events into ledger entries; `ledger.js` (async fake with `failNextWrite()`) and `payments.js` already work. Events arrive duplicated, concurrently, out of order (refund before charge → 409 so the provider retries), and ledger writes fail (→ 500, nothing recorded). Planted flaws: dedupe on chargeId, dedupe on a content hash (drops two same-amount partial refunds), mark processed before applying, refunded total updated before the ledger write, always reply 200, "JS is single-threaded so no race", ack a refund for an unknown charge with 200. Possible follow-up: signature verification over the raw body with a timestamp tolerance (replay window).
- [ ] **Fix a slow report: N+1 queries / O(n²) (Medium, ~40 min).** Multi-file service with a fake DB that counts queries. Tests pin correctness plus a query budget and an operation budget. Planted flaws: a cache that serves stale data, batching that breaks result ordering, "the DB is fast, just add an index" hand-waving.
- [ ] **Refactor legacy code safely (Medium, ~45 min).** One tangled 200-line pricing/discount function. Write characterization tests first, then restructure without changing behavior, including a few odd edge cases that are actually load-bearing. The AI confidently "simplifies" one of them away. Could be the senior version of the Easy refactor item above.
- [ ] **Job queue with leases and a dead-letter queue (Hard, ~55 min).** A worker queue on a simulated clock (`mkClock`): visibility timeouts, lease renewal, retries up to a max-attempts limit, a dead-letter queue, at-least-once semantics. Planted flaws: ack before the work finishes, a lease that expires mid-job and lets a second worker take it, retry counts reset on redelivery.
- [ ] **Second review scenario.** For example a PR adding a cache with an invalidation race, or a PR to an API that silently breaks backward compatibility (renamed field, changed default, stricter validation). Reuses the `"kind": "review"` format.
- [x] **Second debug scenario, built as `build-cache`** (after a Google SWE "solve checksum and dependency debugging tasks" question). A mini build tool caches outputs under a checksum of each target's inputs. Two bugs from `incident.md`: the cache key covers only direct deps' sources, so a change two levels down gives a cache hit for a stale `//app:cli` (the CI log shows the same key before and after); and `buildOrder` uses one `seen` set, so a diamond (`//lib:log` and `//lib:net` both use `//base:strings`) is reported as a cycle. Planted flaws: return early on any seen target (hides real cycles), turn the cache off as "corrupted", blame a 32-bit hash collision and switch to SHA-256.
- [ ] **Third debug scenario.** A memory leak (listeners or timers never cleaned up), or a timezone/DST bug in scheduling. Reuses the `"kind": "debug"` format.
- [x] **Driver payroll (Hard, object design), built as `driver-payroll`.** Second `"kind": "lld"` round, after the Rippling-style "delivery driver payroll" question: `addDriver`, `recordDelivery`, `getTotalCost`, `payUpTo(t)` (pays deliveries that ended by t, never twice, late-recorded ones in the next run), `getTotalCostUnpaid`. Money in integer cents, each delivery rounded on its own. Follow-up: rate changes over time (`setRate(id, rate, from)`), paid at the rate when a delivery starts, and no changes inside a paid period. Planted flaws: one object with parallel maps (design), round only the totals, pay deliveries that have started, pay runs that do not mark anything paid, a paid-up-to watermark (late deliveries never paid), price stored at record time, the latest rate for every unpaid delivery, back-dated rate changes. Possible later follow-up: peak number of drivers on deliveries at once in the last 24 hours (sweep line).
- [ ] **Spreadsheet with formulas (Hard, object design).** Second `"kind": "lld"` round: cells, a dependency graph, recalculation in topological order, cycle detection with a useful error. The follow-up adds new functions or ranges (`SUM(A1:A5)`).

- [x] **Timestamped banking system (Hard, multi-level), built as `bank-levels`.** New `"kind": "levels"`, after the CodeSignal-style multi-level assessment (also the shape of Meta's "coding and AI-assisted" round): four levels, each unlocking when every visible test so far passes. 1: createAccount, deposit, transfer. 2: topSpenders (ties by id). 3: pay with 2% cashback credited 24 hours later, getPaymentStatus. 4: mergeAccounts and getBalance(timeAt). Planted flaws, offered only once their level is unlocked: same-account transfer allowed, tie order left to sort stability, cashback credited only in getPaymentStatus (or with setTimeout), Math.round for cashback, merge rewriting the history of account 1, the merged id still answering getBalance, pending cashback left on the removed account. Other multi-level ideas: an in-memory database with TTL and backups, a file storage system with users and quotas.
- [x] **Debug a queue, then solve array problems (Hard, multi-level), built as `queue-arrays`** (after LinkedIn's "Debug Queues and Solve Arrays" Software Engineer question). Level 1 is debugging: `deque.js` is a ring-buffer deque with four bugs (grow copies `buf[i]` instead of unwrapping from `head`, popBack/peekBack index without the modulo, popFront on an empty deque drives `size` negative, and `at(size)` returns the front item when the buffer is full; the last is caught only by hidden tests). Level 2: `windowMax` (sliding window maximum). Level 3: `shortestSubarray` with sum >= k and negative numbers. The array levels wrap `nums` in a Proxy that counts reads (at most 10 per element) to enforce O(n). Planted flaws: grow the buffer in place with `concat` (keeps head), `(head + size) % cap - 1` for the back index, values instead of indices in the window deque, slice + Math.max per window, two pointers with negative numbers, no back pops on the prefix deque.
- [x] **Build a friend recommender (Hard, multi-level), built as `friend-recommender`** (after Meta's AI-assisted coding round: an existing multi-file codebase, fix it, then extend it). `graph.js` is a working shared `SocialGraph` (its `friendsOf` returns the live Set, with `onChange` events); `recommender.js` is "People You May Know". Level 1 is debugging from three tickets: `exclude.add(userId)` mutates the graph's own friend set (friend count +1), ties sorted with `a[0] - b[0]` on string ids (NaN, so insertion order), and deactivated friends still counted as mutual friends (plus, hidden only, a deactivated user still gets suggestions). Level 2: `block` (both ways, ends the friendship) and `dismiss` (one way), still returning k. Level 3: cache per user, never stale, recomputing only users within two hops of a change; tests count `friendsOf` calls. Planted flaws: "exclude.add is local", a boolean comparator, deactivated friends still bridging, one-way blocks, block keeping the friendship ("the recommender must not change the graph"), filtering dismissals after slicing, invalidating only the endpoints of a change, caching the sliced list per user (ignores k), clearing the whole cache on every change.

## Algorithmic / library-style scenarios

- [ ] **Diff / merge / patch (Hard).** 3-way merge, JSON diff, or an LCS text diff. Subtle edge cases where confident wrong answers slip through.
- [ ] **Dependency resolver / topological scheduler (Medium).** Cycle detection with a useful error, stable ordering, parallel "levels".
- [ ] **Template / expression engine (Hard).** A `{{ }}` renderer with escaping, or an arithmetic evaluator with precedence.

## Difficulty range

Now: two Easy (bill-split, streak-counter), ten Medium (one the code-review scenario, one the debugging scenario), three Hard.
- [x] An Easy warm-up scenario, built as `bill-split` (short, one function, 2 or 3 planted flaws). Chosen: **add a tip and split to a bill calculator** (feature format, 2 or 3 small files, about 25 minutes). Split N ways with cents that do not divide evenly, plus an optional tip percent. Planted flaws: floats instead of integer cents; remainder cents dropped or given to everyone; tip applied after tax when the spec says before. Other Easy candidates: search for a bookmarks list (case-insensitive, `tag:` filter, relevance sort).
- [x] A second Easy scenario, built as `streak-counter` (login/activity streak from a list of dates, with a grace-day parameter, about 25 minutes; `today` and dates are plain "YYYY-MM-DD" strings rather than an injected clock, to keep it simple). Planted flaws: off-by-one in the grace-day gap check (`gap <= graceDays` instead of `gap - 1 <= graceDays`, which breaks even a plain consecutive streak); duplicate dates not deduplicated before counting; no check that the most recent activity is recent enough, so a stale streak from long ago still counts.
- [x] A second Hard scenario: `offline-sync` (queue, idempotent retries, pull/merge with tombstones).
- [x] A third Hard scenario: `middleware-router` (Express-style middleware chain: `next()` called twice, async handler rejections, error-handler order/registration).
